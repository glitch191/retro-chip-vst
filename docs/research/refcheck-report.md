## Diagnosis

Runs of 2026-09-29 (diagnosis) and 2026-09-30 (after the F1 and F2 fixes): 104 Genesis stimuli (VGM) and 44 SNES stimuli (SPC), all generated by
`tools/refcheck/make_stimuli.py` from our own register writes, BRR data and SPC700 program.
Primary Genesis reference: Nuked OPN2 + MAME SN76496 in VGMPlay 0.40.9; second opinion:
MAME / Genesis Plus GX YM2612 + Maxim SN76489 in the same player; SNES reference: Game Music
Emu through FFmpeg 9.0.2. Reproduce with:

```powershell
python tools\refcheck\make_stimuli.py
python tools\refcheck\compare.py --chiptool build\windows-x64-release\dsp\tools\chiptool.exe
```

(about 35 minutes, pure Python analysis; `--only NAME` for a subset, `--no-render` to reuse
the renders in `build-reports/refcheck/renders`). Nulls at the fractional lag, from the same
renders: `python tools\refcheck\fracnull.py [--ref ref_mame] fm_alg0 fm_alg7 ...`.

### Findings F1 and F2: fixes and before / after (rerun of 2026-09-30)

Both findings of the 2026-09-29 run were engine deviations and are fixed; the tables below
are the 2026-09-30 rerun (same stimuli, same references, same analysis). All 325 ctest tests
pass; the NES output is unchanged (its engine still uses the old resampler kernel).

**F1. YM2612: S1 reached the other operators one sample too early. Fixed.**
Cause: `modulatorDelay()` (`dsp/include/chipdsp/genesis/GenesisTables.h`) derived the delays
from the S1, S3, S2, S4 evaluation order alone (S1->S2 0, S1->S3 1, S1->S4 0). Both
references (Nuked OPN2 and MAME / Genesis Plus GX, which agree with each other within 0.3 dB
on fm_alg0..3) behave as if S1 were read from its feedback history register: every S1 path
is one sample later. The rerun showed the same delay on S1 as a carrier: relative to both
references, an S1-alone tone (fm_fb0) came out 0.83 host samples (1.00 FM sample at 44.1 kHz)
earlier than an S4-alone tone (fm_sine_ref). Fix: S1->S2 1, S1->S3 2, S1->S4 1 and S1 as a
carrier (algorithm 7) 1 sample (`kS1CarrierDelay`); S2 and S3 paths unchanged
(`Ym2612Core::computeChannel` reads S1 from `fb1` / `fb2`). Decision and alternative:
`docs/research/genesis.md` Ambiguity 41 and `docs/HARDWARE_NOTES.md` [genesis 41].
Regression tests (`dsp/tests/test_genesis_operator.cpp`): "Pipeline delays: every modulation
path uses its documented sample delay" (every algorithm, outputs recomputed from the operator
formula with the delay table) and "Algorithm 7: S1 reaches the accumulator one sample after
the other carriers"; `test_genesis_tables.cpp` pins `modulatorDelay()`.

**F2. Output path: the band-limited step synthesiser boosted the top octave. Fixed for the
Genesis and the SNES; the NES keeps it (product-owner decision).**
Cause: the kernel was sampled windowed-sinc impulses integrated by a discrete running sum,
which filters every step by `H(w) / (1 - e^-jw)` instead of `H(w) / (jw)`: a gain of
`(w/2) / sin(w/2)`, `w = 2 pi f / fs`. Fix: `BandLimitedStepSynth::Kernel::IntegratedStep`
(taps = first differences of the integrated windowed sinc, so the running sum gives exact
band-limited steps), used by `GenesisEngine` (FM, PSG, per-channel buses), `SnesDspEngine`
(main and per-voice, 32 kHz -> host) and `chiptool regs`. `Nes2A03Engine` keeps the default
`ImpulseSum` kernel so the NES output does not change. Regression tests
(`dsp/tests/test_core_band_limited_step_synth.cpp`): exact settling and centring for every
phase at 32, 53.27 and 223.7 kHz; square-wave fundamentals flat within 0.05 dB up to 13.98 kHz
from a 1.79 MHz source and up to 11.19 kHz from 32 kHz, while the impulse-sum kernel matches
the formula. The change of our harmonic levels between the two runs equals the formula
(fm_dt*_b6 H7 at 12.3 kHz: -1.16 dB measured, -1.14 dB formula).
